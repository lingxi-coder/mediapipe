BoTSORT Integration — Brainstorming Briefing

MediaPipe fork · branch dev · making BoxTracker vs. BoTSORT a user-selectable tracker in the livestream object-detection flow

1What exists today

Tracking currently lives in one place only: the tiled stream path of the YOLO object detector. It uses the BoxTracker — an optical-flow propagator — wrapped as ObjectTrackingSubgraphCpu, fused back through a TRACKER_DETECTIONS seam.

IMAGE ─┬─────────────────────────────────────────────┐ │ ▼ DETECTIONS ─▶ ENCODE label_id→str ─▶ ObjectTrackingSubgraphCpu (BoxTracker / optical flow) │ DECODE str→label_id ◀────────────┘ │ DetectionsTickGate (TICK = fresh DETECTIONS) │ ▼ TRACKER_DETECTIONS ──▶ merge graph ──▶ output

Implication: "add BoTSORT to the livestream flow" most naturally means this same seam. Whether it should also cover the non-tiled stream path is an open scope question (Q4 below).

3The core difference — why this isn't a trivial swap

BoxTracker (today)

Optical-flow propagation. Moves last-known boxes forward by dense pixel motion. Naturally fills SKIP frames. No notion of a stable object identity in the output contract.

BoTSORT (proposed)

Tracking-by-detection. Kalman motion prediction + Hungarian/lapjv association + global motion compensation. Emits persistent track IDs. On a detection-less frame it Kalman-predicts forward (also a valid gap-fill).

Their interfaces line up (frame + detections → detections), so BoTSORT can be a drop-in alternative at the seam. The real question is what to do with its signature feature — track IDs.

4Decision needed now — output contract

How should BoTSORT's persistent track IDs show up in the detector's output?
A · Parity drop-in, IDs internal recommended to start

BoTSORT is an alternative tracker behind the same output contract as BoxTracker — no track-id field exposed. Reuses the existing TRACKER_DETECTIONS seam unchanged → smallest blast radius. Track IDs can be surfaced in a later follow-up.

B · Surface track IDs (new capability)

Expose the stable per-object ID on each output Detection (e.g. detection_id / a track-id field). Genuinely more useful for livestream apps, but the public output contract changes for the BoTSORT path and there's more to design + bind.

Reversible: starting at A and adding B later is cheap. Starting at B commits the public contract up front.
